# Grill 两批六题与可空多选（2026-09-06）

## 授权与冻结要求变化

用户先要求 Grill 每批最多并列 3 个问题，每题可以多选、单选或不选，整批统一提交；跳过不得被解释为采用推荐项或确认隐含约束，依赖上一批答案的追问应留到下一批。随后用户明确覆盖原五题预算：“不要保留5题了，直接发两批，6题之后再说什么需求没确认”。

因此这次同时调整冻结 G2、G3：新任务固定 `3 + 3` 两批共 6 题，回答完第二批后才生成最终确认和未决事项；第一批后不能提前确认。G1 的独立 Grill 上下文和最终人工确认继续保留。页面不展示题数预算等设计解释小字。

## 数据与 API 契约

- `GrillState.questions` 保存当前批次，`question` 继续指向首题以兼容旧单题状态；新生成问题带稳定 UUID `id`。
- `round` 是累计已发问题数，也是防止旧批次串答的版本标识。新任务首批为 3、第二批为 6。已有 1、2、4、5 题等旧状态从当前问题继续，后续每批不超过 3 题，直到补足 6 题。
- `POST /api/runs/:id/grill` 新增 `answers` 数组，通常每个当前问题对应一项，可携带 `questionId`、多项 `choices` 与自由补充 `answer`。每题的空 `choices` 和空 `answer` 合法；整批提交 `answers: []` 表示全部跳过。两者都保存为 `skipped: true` 与“保持未知”。
- 新批次统一提交；遗漏题目、串入旧题、无效选项或同时混用批量与旧单题格式会明确拒绝。正在生成一批时 Manager 串行化 Grill 请求；完成后旧 `round` 过期，因此重复提交不会推进两次或把答案串到下一批。
- 用户回答先保存到 `pendingAnswers`，再请求模型生成下一批或最终清单。模型连接、JSON 格式、提前确认或题数错误时，当前问题、round 和本批原回答都会持久化；刷新后可以原样重试或编辑后重试，不需要重建任务。重试请求完全省略回答字段表示复用暂存答案；显式 `answers: []` 表示将本批改为全部跳过；显式完整答案表示更新暂存内容。只有生成合法结果后，暂存才并入 `answers` 并清除。
- 已保存的旧 `question`、旧 `{ question, answer }` 历史及模型返回的单题 JSON 继续兼容。旧接口格式只可回答实际的单题批次；面对多题批次会要求刷新界面，不会默默跳过其余问题。
- bootstrap 能力包含 `grill-batch-v1`。

## 模型与确定性边界

一次独立 Grill 模型请求生成一批问题，不启动三个并发模型请求。同一批问题必须彼此独立且选项可组合；依赖第一批答案的追问只能在第二批生成。多选中的冲突必须完整传给模型，由下一批继续澄清，或在最终 `unresolved` 明示，不能静默退化为单选。

`skipped: true` 只表示未知。后端不会信任模型把确认要求归因于空选：最终“已明确的要求”由原始有效要求和未跳过的真实回答确定性组成，模型返回的 `constraints` 不直接采用。每个跳过的问题还会确定性追加为 `未指定：问题`，进入最终 `unresolved`。模型补全只能进入 `assumptions`，必须由人最终确认；`confirmGrill` 对 assumptions/unresolved 的人工门禁保持不变。

新会话在回答满 6 题前若模型提前返回 confirmation，会明确拒绝；回答满 6 题后若模型继续追问，也会拒绝。旧单题状态可按剩余题数逐步补足，不删除或重写既有回答。
