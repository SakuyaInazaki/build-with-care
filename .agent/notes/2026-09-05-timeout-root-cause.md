# 长等待与 timeout 的实际原因

日期：2026-09-05。用户要求立即定位反复出现的“十分钟 timeout”。本次只核对代码、运行事件和模型原始响应，不启动模型请求、不改动任务或模型设置、不重启服务。

## 证据

核对本机测试任务 `f7629f25-8b60-4375-ac9d-78e92237f637` 的 `events.jsonl`、`dsh-events.jsonl`、`state.json`。以下时间为北京时间，原始记录为 UTC。

| 阶段 | 时间或耗时 | 原始证据 |
| --- | --- | --- |
| 第一次执行模型请求 | 19:06:29.904 至 19:16:44.659，614.755 秒 | 产品事件 26 至 27 |
| 第一次响应 | 输入 1,409 token，输出 44,883 token | 原始 assistant/message 的 usage；推理块 146,808 字符，工具调用为 list_files，参数为 `{}`，正常以 tool-calls 结束 |
| 列文件 | 提出到完成 0.022 秒 | 产品事件 27 至 29 |
| 第二次执行模型请求 | 19:16:44.690 至 19:19:24.672，159.982 秒 | 产品事件 30 至 32；响应输入 46,322 token、输出 20,342 token，写文件参数 67,805 UTF-8 字节 |
| 写入前审查 | 8.016 秒后失败 | 产品事件 32 至 33；review.source=system、topic=review-failure、summary 为原始 TimeoutError 消息 |
| 人工处理期限 | 预设到 19:29:32.688 | gate.expiresAt；实际在 19:20:39 用户停止后 cancelled，没有 gate.expired |
| 更早一次执行超时 | 18:50:14.740 至 18:52:14.757，120.017 秒 | 产品事件 21 至 22，来自此前执行适配器沿用的 120 秒默认截止时间；该执行截止时间已移除 |

## 定位结论

1. 十分钟长等待发生在模型生成阶段。模型先生成了约 14.7 万字符的推理内容，包含大量应用方案和代码草稿，随后才调用列文件；工具本身没有运行十分钟。该响应成功返回，不能称为十分钟执行超时。模型配置为 DeepSeek V4 Pro、最高推理强度；不能把当前证据夸大为最高强度必然导致每次请求如此缓慢。
2. `server/models.ts` 的 `complete()` 固定发送 `stream: false`；`CompatibleAdapter.stream()` 先等待完整结果，再一次性转成 dsh 流式块。原始记录也显示推理块、工具块及用量信息都集中在响应结束的毫秒内出现。前端在漫长生成过程中看不到增量进展，这是实际的适配器问题。非流式处理隐藏进展，但不会凭空生成十分钟推理，改成流式也不能保证模型立刻完成。
3. 真正显示的 TimeoutError 来自 `engine.ts` 在调用审查模型前建立的 `AbortSignal.timeout(reviewTimeoutMs)`，本机值为 8000。外层信号先中止，直接携带原生英文消息；`complete()` 的 signal.aborted 分支优先抛出该 reason。审查需读取约 67.8 KB 的写入参数，本机审查模型同样使用最高推理强度，当前等待设置与这类调用存在明显冲突。由于没有保存该次被取消的上游审查增量，不能声称知道审查具体生成了多少 token。
4. 当前服务仍运行的旧 catch 分支把上述技术异常制造为 uncertain 人工决策，继而进入十分钟人工门禁。这解释了 timeout 为什么出现在“需要你判断”，以及界面如何将模型生成、审查失败、人工等待混淆。已提交的 review.failed 修复解决错误归类，但尚未部署到该进程。
5. 代码中的 600000 对应人工处理期限，符合冻结需求第 5 节的默认审批等待；它不是这次执行模型请求的期限。执行调用明确使用 timeoutMs=null，没有新增十分钟执行定时器。原始记录中也没有十分钟重试循环。

## 后续修复边界

- 执行适配器应真正消费上游 SSE，提供生成阶段进展并保留用户主动取消；不以新截止时间、隐式输出上限或静默降低推理强度处理长推理。
- 审查技术失败继续保持未执行状态，独立于真实业务判断；恢复操作不得伪装成新增需求。部署前检查是否存在活动任务。
- 审查等待的默认值与配置、是否需要重新设计审查请求的组织方式必须单独处理；不能把拉长人工审批时间当成修复审查超时。
