# 验证闭环与撤销模型请求次数上限

## 用户授权与问题

用户明确要求移除未经提出的“每轮 30 次模型请求上限”，并修复等待验证卡片长期停留、没有后续处理的逻辑。不得以新增任务绕过、提高为另一个任意次数上限或将静态检查宣称为完整功能验收。

此前核对 Mario 任务：实际存在当前文件的 HTML、内联 JS、外部资源静态检查且通过，没有正在执行的 verify_app。旧单元自己的证据因后续同文件修改失效，前端又只接受原单元检查步骤，遗漏后续同文件有效检查；普通有决策单元还仅在人工纠正路径绑定验证。没有自动重新验证队列。这些是实现缺口。

## 本次源码与语义

- 去除执行 onRequest 的 30 次异常分支；requestCount 只记录请求序号。没有替代数值上限，显式停止和现有真实错误处理保留。
- 工作单元 end_unit 正常结束时，Host 自动检查该单元成功 write_file/edit_file 的去重路径。真实检查步骤、文件 hash、当前约束版本和结果持久化；失败返回给执行模型，不能将该单元标为完成。允许取消后声明修复单元，取消本身不伪造验证。
- 扩展固定检查到独立 JS（Acorn）、CSS（PostCSS）、JSON 语法。HTML 保留原有静态规则。未知类型明确报告无自动规则；不把语法通过视为功能正确。
- 增加 POST `/api/runs/:id/verify`，要求现行 revision 与 UUID requestId，重复请求幂等；只允许非运行、非澄清状态。只重新检查当前产物，不发模型请求、不恢复执行、不改要求或清除原错误。
- 前端普通完成单元的检查按实际写入路径、当前文件 hash 及约束版本关联，允许使用后来对同一当前文件的真实检查。所有涉及路径均须覆盖且检查通过才进入已验证。人工纠正仍需对应的验证关联，不以普通静态检查自动认可或验证任意纠正。
- “重新检查文件”入口只在 bootstrap 后端版本 `unified-work-units-v3` 且任务空闲时显示，防止前端先更新造成接口不存在。
