# 当前产品与冻结需求的缺口核查

> 本文前半保留合并前核查快照，末尾“合并后的复核”是当前交付状态。已补齐的项目不能继续读作缺失，也不能据此将其余缺口宣称完成。

## 结论和核查范围

用户追问工作单元是否实现，并要求诚实列出所有未完成内容。本记录核查的是当前默认启动入口实际连接的 `frontend/` → `decision-desk/server/`，不是把仓库各处曾实现的功能合并计为产品能力。

**当前产品未达到冻结首版验收标准。** 以下是代码与既有测试证据核查，不是新一轮 24 项正式验收，不以单元测试总数代替冻结评测通过数。本轮只记录差距，不修改冻结需求、不自动迁移后端或任务数据。

## 两套后端是什么

- 根 `package.json` 的 start/dev 指向 `frontend/`；`frontend/start.mjs` 启动 `decision-desk/server/index.ts`。当前接口为 `/api/runs/...`，数据在 `frontend/.data/runs/`。
- 旧 `src/server.ts`、`src/stream.ts`、`src/llm/agent-runner.ts` 使用 `/api/sessions/...`，包含 `executeUnit`、`begin_unit`、`end_unit` 等机制。根启动脚本将其保存在 `*:legacy` 名下。
- 当前后端没有导入这些工作单元机制。类型是 RunState/Step/Decision/Gate，不含工作单元声明与生命周期。
- 两套代码存在不等于两个服务同时运行；旧实现有代码不等于当前产品具备该能力，也不等于旧实现自身符合所有冻结项。
- 此差距在 `docs/frontend-redesign-audit-2026-09-05.md` 与 `frontend/README.md` 中已有记录，但未落实补齐，交付沟通也未充分突出。不能以这些文档存在为已经完成开脱。

## 已确认的主要缺口

| 项目 | 当前实际情况 | 证据 |
| --- | --- | --- |
| 工作单元与任务切分 | 没有语义子目标 → 声明决策 → 工具序列的 Host 契约；当前每次工具调用单独审查 | `decision-desk/shared/types.ts`；`server/engine.ts` 的 preExecute；旧 `src/llm/agent-runner.ts` 的 begin_unit/end_unit 未接入 |
| 单元级审查隔离 | 每次请求独立生成消息，但会携带全任务最近 4 个步骤、5 条人工输入。没有单元开始、单元内上下文与销毁边界，不能声称 0 跨单元共享 | `server/reviewer.ts` 的 createReviewer、recentSteps、recentHumanInput |
| 声明校验与规则硬下限 | 真实审查主要依赖模型分类。约束 ID/证据格式校验和路径保护已有，但不等于独立语义硬规则；示例中的确定性内容规则主要位于 demoReview | `server/reviewer.ts` 的 parseReviewResult、demoReview、createReviewer；`server/workspace.ts` |
| dsh 工具范围与不可逆动作 | 只注册 list_files/read_file/write_file/edit_file/verify_app 五个工具。shell、其他 dsh 工具及外部不可逆动作标记/审查路径未接入。系统提示将能力限制为小型 HTML/CSS/JS 页面 | `server/engine.ts` 的 registerTools、systemPrompt |
| 并行检查 | maxParallelToolCalls=1 对全部工具串行，尚无检查并行、写入串行的分别调度 | `server/engine.ts` 的 AgentLoop 配置 |
| 错误收敛与重复违规 | 普通工具错误返回模型并计数，但第三次调用 requestStop；不是明确的阻塞求助状态。未见重复相同违规立即暂停的专门判定。不能将提示词“不要重复”当作 Host 实现 | `server/engine.ts` 的 tools/result、waitForHuman、requestStop |
| 通用修补验证 | 产物 hash 与 stale 已实现；自动检查只覆盖 HTML 结构、内联 JS 语法及少数存储/资源/密码框静态规则。将纠正标为 verified 的自动关联主要针对“内存/刷新/持久化”关键词，不是任意需求的验证计划。一般功能与交互未被完整自动验收 | `server/engine.ts` 的 verify；`server/workspace.ts` 的 inspectHtml |
| 保存前脱敏 | Store 直接序列化状态、事件、原始 dsh 日志，没有统一保存前脱敏管道。API 不返回配置密钥、设置文件 0600，不能替代任务内容及工具输出脱敏 | `server/store.ts` 的 append/save/recordRaw |
| 短期 token | token 在服务启动时随机生成且整个进程共用；cookie 有 24 小时 maxAge，但服务端未校验 token 到期时间。loopback 和来源检查已有 | `server/app.ts` 的鉴权与 bootstrap |
| 正式验收 | 未找到当前链路完成冻结 24/24、3 次完整真实闭环的充分报告。已有真实请求与红卡，不足以证明全部门槛达成；旧演示脚本和模拟模型测试不能替代真实验收 | `docs/requirements-v1-frozen.md` §9；当前测试与 notes |

此外，执行仍有每轮 30 次模型请求限制，文件仍有 250 KB 上限及扩展名范围。这些是实际实现限制，不能宣传为通用、不受这些限制的执行能力。执行/审查取消固定总超时不意味着已经不存在其他运行限制。

## 用户后续反馈和未上线改动

- 模型设置同步：补丁已写并通过后端/前端测试；当前进程尚未加载此后端补丁。当前用户任务在显式继续后实际已用 Flash，不能把这当作热更新补丁已上线。
- 看板折叠：本轮写了各栏折叠、已验证默认收起、栏内滚动的源码；用户转向追问核心缺口后暂停，尚未测试、构建或浏览器验证，不能称已完成/上线。仅展示层变化，不删除记录或改变验证状态。
- 澄清多选、删除“需求澄清 · 尚未开始 / 最多 5 题”、连接成功提示增强：仍未实现。原 `user-testing-feedback-pending` note 记录用户当时要求暂不修改；现在核查仍是 radio、该小字仍在、成功提示仍为普通绿色文字。需如实列为待办，而非把“已记录”称作“已做”。
- 卡片底色增强、横向时间线、原始记录详情、独立继续任务、证据数组兼容、编辑错误归类等已有实施记录；这些局部完成不补足上列核心缺口。
- 最近后端 52 项、前端 9 项测试是现有实现的回归测试，不是冻结 24 项；旧根工程测试也不能算作当前产品能力证明。
- 用户要求 push 的检查点已推送；之后本地新增的修复仍有未提交/未推送内容，不能把本地工作区等同于远端成果。

## 后续修复应依据什么

先确定并落实唯一的当前运行链路与工作单元契约，再接入审查上下文边界、Host 硬规则、工具调度与验证。旧实现只作为经过重新核验的候选代码，不直接整套替换，不重启正在执行的任务，不把两套不同语义的测试成绩相加。修复完成后逐项提供冻结验收证据，最后进行三次真实闭环。
