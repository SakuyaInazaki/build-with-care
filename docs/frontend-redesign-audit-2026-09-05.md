## 2. 赛道真正要求什么

赛道三的命题是“给 Multi-Agent 时代，造一个人还在场的工作台”。原文包含两个目标：当下能控制 Agent，以及长期能积累自己的判断。四个参考方向并非要求全部实现；因此单执行 Agent 的首版与赛道名称没有矛盾。

本产品应优先服务用 Agent 做项目的学生和不读代码的协作者，让他们回答三件事：

1. 它正在替我决定什么，这会影响什么？
2. 哪项违背了已确认要求，我现在能怎样纠正？
3. 我的纠正之后发生了什么，哪些结果有验证证据？

“人还在场”应由需求最终确认、冲突处理和判断记录体现。正常写入不需要人为点击；不能为了表现人的参与而制造审批负担。复盘可以呈现判断与结果的关联，不能直接宣称证明了长期能力提升。

仓库保存的赛事说明写明：本地可运行 Demo、1 页以内项目说明、可运行代码及 README、2 分钟路演；作品于 9 月 6 日 12:30 冻结。本次公共网页检索没有找到可独立核验的同一赛事公告，因此这里只记录仓库赛事原文，不声称已核验最新现场安排。

### 外部产品核对

旧研究中“没人做”“周边都做完了”等绝对判断不宜直接沿用。本轮只核对了与定位直接相关的两类官方资料：

- Vibe Kanban 的官方评审流程围绕 Agent 完成后的 diff、行内评论和反馈修复展开。这可供借鉴成果检查与反馈布局。[官方文档](https://www.vibekanban.com/docs/reviewing-code)
- LangChain 已提供工具调用前暂停、人工批准、编辑与拒绝等机制，执行前介入本身不能作为独有能力宣传。[官方文档](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)

据此作出的产品判断是：本项目应把优势落在中文语义决策、人的约束与实际动作对账、向后纠正、证据绑定及判断复盘这一整段体验上。此次核对不足以证明市场唯一性。

## 4. 与冻结需求的主要差距

以下为代码审视结果，不是完整的 24 项冻结验收结果。

| 冻结项 | 当前证据 | 对重设计的影响 |
| --- | --- | --- |
| G1–G4：独立多轮 Grill、最多五轮、补全与未决处理、最终确认 | `manager.ts` 按标点拆原文；`App.tsx` 的 `Baseline` 是一次性约束编辑。根工程提供单次 spec draft，也不是完整 Grill | 新增逐题澄清和最终确认两种页面状态；需要真实 Grill 接口与独立上下文 |
| B1：状态分栏、待处理卡并列 | 新界面以 `TimelineEvents` 排时间；`gates.find(...)` 选中首个待处理项，右侧仅渲染一个 `DecisionPanel`。历史步骤可在时间线查看，但不是状态看板 | 重建主视图，全部待处理卡应可扫描；详情展开不能遮住其他卡 |
| B2：蓝卡自动继续、认可／纠正／未审阅 | `humanStatus` 与自动继续已有；操作集中在单卡面板，列表主要强调执行状态 | 保留独立的人类审阅状态，使“已执行”和“已认可”明显不同 |

## 6. 建议的重设计主线

**需求澄清 → 最终确认 → 决策看板 → 卡片内纠正 → 受控验证 → 判断记录。**

| 场景 | 首要内容与操作 |
| --- | --- |
| 开始任务 | 一句需求与明确的下一步；不把固定演示作为默认真实任务 |
| Grill | 每轮一题、2–4 个选项、自由输入、轮次；结束时列出模型补全和未决项，等待最终人工确认 |
| 执行看板 | 按状态分栏，首先能找到全部待处理项；卡片承载工作单元语义，不把每条工具日志升级为大卡 |
| 卡片详情 | 左边人的约束与版本，右边拟执行／已执行动作、审查、证据；所有待处理卡仍可见 |
| 纠正 | 红卡保留四个业务动作；蓝卡体现认可／纠正／未审阅且不阻塞；反馈说明是否更新约束与影响后续 |
| 成果与验证 | 产物预览、当前内容对应的检查、失效证据与剩余未验证范围；适配网页以外的产物 |
| 判断记录 | 串起人的决定、约束变化、后续修补与真实检查；不评分、不把未审阅算认可 |

分栏名称可在实现中细化；这是展示分组建议，不是新增服务端状态。分栏依据执行／处理状态，红蓝灰等语义颜色与人工审阅状态保持独立。

视觉方向：安静、清楚、有工具感。采用系统中文字体、浅中性背景、统一间距与有限字号；让品牌色减少对红／蓝／绿证据语义的干扰。只在导航或非阻塞浮层使用适量透明材质，卡片正文保持稳定高对比度。状态更新不抢焦点、不反复自动滚动；新红卡用明确提示和定位入口让人找到。

开始实施时，先落地“运行中出现真实冲突”的纵向完整流程：工作单元材料 → 审查 → 红卡 → 四动作 → 约束与调用状态 → 新验证证据。接着补齐 Grill、其他状态、报告和数据管理。每段都对照冻结用例，而不是以旧页面测试通过作为完成标准。
