# 需求对齐 · grill-me 访谈决策记录

> 2026-09-04，访谈人：芝士（AI），受访：Yonack1。
> 方式：一次一题，逐分支敲定。本文档随访谈增量更新。

## 已敲定的决策

### D1 · 定题：做「决策流」（Decision Stream）

- **决策**：参赛作品方向拍板为决策流——agent 干活时把"你没指定、我自己定了"的隐性决策实时变成卡片给人拍板，可翻案，翻案只向前生效，翻案记录构成贡献证明。主攻方向一，顺带吃方向三。
- **过程**：受访人要求先重新过一遍全部候选方向（官方四方向 + 历史讨论想法），逐个对照 research.md 的竞品调研结论后，确认红灯区（编排/降门槛/行级归因/只读观测/回滚/会诊）不碰，回到决策流。
- **依据**：research.md 第四节——"运行中决策层"与"干预归因"是仅有的两个已验证空白。

### D2 · 静默阈值：只弹红卡，蓝卡静默进侧栏

- **决策**：只有红卡（与既有计划/约定冲突）弹出打断人；蓝卡（agent 自由发挥、你没指定它定了）静默流入侧栏，人有空再翻；灰卡（纯执行）不产生卡片。
- **理由**：打断预算极小——审批疲劳的失败案例（Slack 审批按钮 → rubber stamp）表明弹卡越多越接近"什么都没做"。宁可漏也不刷屏。
- **牵出的依赖**：红卡定义依赖一份 baseline（计划/约定）做对照 → 见 D3。

### D3 · baseline 来源：一句话需求 → agent 扩写 spec → 人确认

- **决策**：人给一句话需求，agent 扩写成 spec，人确认后开工；确认过的 spec 即红/蓝判定的 baseline。
- **理由**：比"强制 plan 模式"更贴近真实使用（人本来就只有一句话）；比"边跑边累积"开局就有对照物。demo 动线里"人拍板"出现两层（确认 spec + 翻案卡片），对赛题"人还在场"的回应更完整。
- **注意**：spec 确认这步在 2 分钟路演里必须够快，spec 要短（几条要点，不是长文档）。

### D4 · 翻案交互：备选项 + 自由改写 + 紧急叫停，三档齐备

- **决策**：点开一张卡后，人可以——① 点选 agent 自带的 2–3 个备选方案；② 自由改写一句话（"这里应该用 X"）；③ 严重时直接叫停当前任务。①② 注入后只约束后续步骤，不回滚已完成工作。
- **理由**：三档对应三类用户/场景——非技术同学点选项（吃掉方向三）、技术同学写约束、失控时有急刹。叫停是安全底线，也让"管得住"在路演里有一个最直观的演示点。

### D5 · 技术路线：B——Agent SDK 自建壳

- **决策**：用 Agent SDK（建议 TS）自建 harness + Web 前端。审批走 canUseTool / 进程内 PreToolUse hook（先于权限链，保证卡点全覆盖），官方保证回调可无限期挂起——没有路线 A 的 hook 超时 fail-open（超时放行）问题；翻案注入直接以新消息插入对话；叫停用 interrupt。
- **理由**：D2（阻断式红卡）、D4（紧急叫停）在 B 路线下实现最干净，审批日志全在自己进程里，贡献报告零解析成本。接受的代价：要自己做 agent 工作界面（约 1.5–2 人日，工作量易被低估），放弃"原生 Claude Code"演示光环。
- **连带影响**：Day1 实测项收窄——注入通道不再依赖 CLI hooks 文档存疑处，主要剩"plan/spec 文本从哪拿全"一项；Python 侧 streaming 有坑，选 TS 避开。

### D5-R ·（修订，2026-09-04 晚）技术路线改为：给 dsh 写决策流插件

- **决策**：底座从 Claude Agent SDK 自建壳改为 **DeepSeek Harness (dsh) 插件**，锁死版本（0.1.3-alpha.1）赛期内不升级。拦截走 `tools/pre-execute`（全参 + deny 附理由 + 无限挂起 + fail-closed），注入走 `agent.inject()`（原生只向前生效），叫停走 `agent.cancel()`，UI 用自带 Web UI + Slots 加卡片/时间线面板（抄现成 `ui-approval` 插件形态）。
- **理由**：源码级核查（见 <docs/research-dsh-Y.md>）确认四个核心需求全部有原生口子，且**免掉路线 B 最大工作量（自建界面）**；无 Claude hooks 的超时放行隐患；路演叙事加成（"给 95k star 的 dsh 补上决策层"）。
- **已知代价与对策**：Cordis 框架学习成本（有 cookbook permission-gate 示例可抄）；alpha 破坏性变更（锁版本）；不能改写工具入参（翻案本就走 deny+注入，无碍）；自定义事件桥浏览器要走已桥接 waterfall 或自建路由（调研已给路径）。
- **原 D5（SDK 自建壳）保留在上方作决策轨迹**；降级链变为：dsh 插件 → 路线 A（CLI hooks + 简易审批服务）。

### D6 · 贡献报告：时间线回放

- **决策**：机制③做成时间线回放——决策卡按时间排列（含裁决：放行/翻案/叫停），可一步步回看"人在哪拧的方向"。不做完整统计报告页，也不砍掉。
- **理由**：时间线是三个选项里"叙事性/工作量"比最好的：路演收尾能讲故事（这个人在第 3 张卡拧回了方向），本身即"人变强了"（赛题第二层）的成长记录；数据源就是审批壳自己的裁决日志（D5 路线下零解析成本）。

### D7 · demo 场景：现场做小应用，预埋决策点

- **决策**：路演 demo 为现场让 agent 做一个小应用，需求文案里预埋 2–3 个必踩的决策点（如：不指定存储方案 → 必出蓝卡；某处与已确认 spec 相抵 → 必出红卡）。
- **理由**：2 分钟路演容不得"等 agent 恰好犯错"；预埋是唯一能保证红卡稳定出现的做法。要求 Day2 用预埋需求反复彩排，验证触发率后把台词固定下来。

### D8 · 人力：两条线并行（壳 / 前端）

- **决策**：队里有能写代码的队友，分两条线——①壳线：SDK harness、卡点拦截、卡片抽取、翻案注入、叫停；②前端线：卡片流 UI、审批交互、时间线回放。开工第一件事是约定两线之间的接口（卡片数据结构 + 裁决回传协议）。
- **理由**：路线 B 工作量的大头（自建界面）正好可以并行消化；接口先行避免合流时对不上。

### D9 · 节奏：按倒排计划跑

- **决策**：43 小时按芝士产出的倒排计划执行，见 <docs/plan-43h-Y.md>。关键里程碑：9/5 14:00 两线合流出丑版端到端（这也是 dsh 路线的 go/no-go 点：届时挂起审批还没跑通就降级路线 A）；9/6 上午只彩排不加功能。
- **砍单规则**（落后时按序砍，写进计划）：时间线回放降级为静态列表 → 叫停不进 demo → spec 确认简化。**不可砍**：红卡阻断 + 翻案向前生效——这是相对所有现有产品的核心差异。

## 访谈总结

九个分支全部敲定：做决策流（D1）；只弹红卡、蓝卡进侧栏（D2）；一句话需求扩 spec 作 baseline（D3）；翻案=备选项+改写+叫停三档（D4）；技术底座为 dsh 插件（D5，后经 D5-R 修订，原为 SDK 自建壳）；报告做时间线回放（D6）；demo 现场做小应用、预埋决策点（D7）；壳/前端两线并行（D8）；按倒排计划跑（D9）。

尚未对齐、留给开工后的：预埋决策点的具体设计（Day2 彩排前定）、卡片数据结构与裁决协议细节（开工第一小时两线共同定）、路演台词。
