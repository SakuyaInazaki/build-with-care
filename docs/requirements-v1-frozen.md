# 首版需求冻结基线

**冻结日期：2026-09-05**

## 1. 文档效力

本文件是首版实现与验收基线。`docs/requirements-alignment.md`、`docs/requirements-alignment-S.md`、`docs/requirements-alignment-Y.md` 三份 P/S/Y requirements 平权保留为来源；它们不被删除、覆盖或改写。《三种观点权衡与实现方案》是收敛建议，不是高于本文件的规范。来源或建议发生冲突时，以本次人工确认的冻结项作为首版执行语义。

后续任何语义变化都必须先取得人工确认，并写入对应的 note；没有人工确认和 note，不得以实现、测试、演示或文档推断出新语义。

## 2. 产品范围与禁止项

- 首版包含一个执行 Agent 和一个隔离审查模型。审查模型可以与执行 Agent 使用同一种模型；“隔离”指上下文和权限隔离，不要求模型供应商或模型名称不同。
- 主界面只有 `forward-only` 纠正模式。多 Agent、fork、branch API 仅作为隐藏的实验能力保留，不算首版公开产品能力。
- `dsh ask_user_question` 与 dsh subagent spawning 硬禁用。所有需求澄清走工作台 Grill，运行中干预走决策流卡片，均不得走 `dsh ask_user_question`。
- dsh 除上述两项外的全部工具可用，但仍须经过本文件规定的执行与安全策略。

## 3. Grill（需求澄清）

- Grill 使用独立的多轮上下文，不与执行 Agent 或审查工作单元共享上下文。
- 每轮只问一题；每题提供 2--4 个选项，并提供自由输入。
- 最多进行 5 轮。模型判断需求是否完备后，必须再取得最终人工确认，确认前不得开始执行。
- 模型可以对需求作合理补全，但补全内容必须展示并经人工确认。
- 仍未决的项目必须列出；由人输入或明确确认保持未指定。未指定不等于模型可以默默替人拍板。

## 4. 审查与工作单元

- 审查按工作单元进行。每个工作单元都是一个语义子目标、该单元的决策和其工具调用序列。
- 每个工作单元启动一个全新的审查上下文，0 共享上下文；同一工作单元内可以复用该上下文；工作单元结束后销毁。
- 审查模型无任何工具权限，只读取被提交给它的工作单元材料和必要的人工约束。
- Agent 必须声明工作单元及其中的决策；Host 必须校验声明与实际工具调用、人工约束和工作单元边界。
- 判定同时使用通用语义判断和规则硬下限。通用判断不能放宽规则硬下限。
- 可信的只读工具可以直通；shell 永远受控，不因命令看似只读而绕过 Host。
- 正常情况下，记录员/审查结论可以记录自作主张或偏差；是否阻断由独立安全策略和本文件的冲突规则决定。

## 5. 调度、安全与失败收敛

- 检查可以并行；写操作必须串行执行。
- 无冲突且通过审查的写入自动执行，不要求人为逐次点击放行。
- 约束冲突或审查失败必须 fail-closed，不能自动放行。
- dsh 除 `ask_user_question` 和 subagent spawning 外的全部工具可用；外部不可逆动作仅在冲突或审查异常时进入审批，但必须显式标记为不可逆。
- 审查等待默认 8 秒；审批等待默认 10 分钟；二者均可配置。
- 普通运行错误自动重试，连续 3 次仍失败后向人求助并阻塞。重复违规不重试，立即暂停。
- “停止”必须真实收敛：停止后不得继续产生执行、写入或成功证据事件，迟到结果也不得把已停止的状态改回成功。

## 6. 卡片看板

- 看板按状态分栏，而不是按审批队列堆叠。
- 蓝卡表示高影响领域中的 Agent 自主决策：自动继续，并提供“认可 / 纠正 / 未审阅”三种状态。
- 红卡提供四个动作：按原要求改正（内部 API：`rewrite`；拒绝当前调用，原约束不变，要求 Agent 重提）；改成另一种做法（内部 API：`alternative`；保存新的已确认约束版本，拒绝旧调用并重提）；仅本次允许（内部 API：`allow`；精确调用哈希例外，不解除约束）；停止任务（内部 API：`cancel`；进入真实收敛）。
- 单次例外必须绑定被批准内容的精确哈希；只对该次精确内容生效，不能扩大为通用许可。
- 所有待处理卡必须并列展示，不得用单一弹窗遮蔽其他待处理项。
- 双栏布局用于卡片详情：左侧显示人的约束/声明，右侧显示 Agent 实际动作、审查结果和证据。
- 约束版本变化会使尚未释放的卡片过期；过期卡必须按新约束重新审查，不能沿用旧结论。

## 7. 纠正与修补语义

- 首版只公开 `forward-only` 状态链，不公开回滚；实验 fork/branch API 不构成首版能力承诺。
- 纠正通过新增约束和后续状态推进实现，不改写历史事件，不撤销已完成动作。
- 修补后的产物必须重新验证；只有新的受控验证证据通过，问题才算解决并可进入已验证状态。
- 人工验收或人工 `verify` 只记录为人工证据，不使卡片变绿；绿只能由受控执行器绑定的真实通过证据产生。

## 8. 验证与数据

- 自动验证必须是受控检查，并记录 artifact hash。产物发生变化后，原验证自动失效，必须重新检查和重新计算 hash。
- 服务端保存前必须脱敏；会话访问使用短期随机 token；服务只监听 loopback。
- 数据永久保存，但必须支持物理删除；删除操作写入独立的删除审计，审计不能与被删数据共用可被一并删除的记录。
- 服务重启后可以恢复查看已持久化的状态和时间线；运行中的任务视为中断，不得假装从原执行点继续。

## 9. 摘要、演示与评测

- 摘要只作记录和叙事，不评分，不参与通过/失败门槛。
- 真实演示禁止故障注入；演示中的红卡、修补、验证和报告必须来自真实执行链路。可准备录屏作为故障兜底，但不得把注入故障冒充真实演示。
- 具体演示任务尚待提供；在任务提供前，不把任何预设任务当作已冻结的演示任务。
- 至少完成 3 次真实闭环；其中至少 1 次必须产生真实红卡。真实闭环是从确认需求开始，经执行、必要纠正、受控验证，到报告/结束的完整流程。

### 24 条首版评测集与精确门槛

下表每一项均为必测项。每项只记通过或失败；不得用摘要分数抵扣失败项。

| 看板 | B3 | 红卡四动作 | 按原要求改正、改成另一种做法、仅本次允许、停止任务四项业务语义均可用，且分别正确拒绝并重提、保存新约束后拒绝并重提、按精确调用哈希仅本次例外、进入真实收敛 |

## 10. 已接受风险与边界

以下不是遗漏，而是本次人工确认后明确接受的风险：

- dsh 全工具可用，仅 `ask_user_question` 与 subagent spawning 禁用。
- 不可逆动作不做额外的常规审批，只在冲突或审查异常时审批，并强制标记。
- 同一种模型可以承担执行和审查，但审查上下文、权限和工作单元生命周期必须隔离；这被称为“异源”时，含义是隔离的审查来源/上下文，不是供应商必须不同。
- 实验 API 保留，但多 Agent/fork/branch 不算首版能力，也不出现在首版主界面。
- loopback、单用户和重启中断是首版边界，不扩展为认证、多进程并发或任务续跑承诺。

## 11. 变更控制

后续任何语义变化，包含范围、状态链、卡片动作、审批时限、工具权限、隔离边界、验证绿灯条件、数据删除语义和评测门槛，都必须人工确认，并在 `.agent/notes/` 写入带日期的 note，说明变更内容、理由和影响。未完成该记录前，现有冻结语义继续有效。
