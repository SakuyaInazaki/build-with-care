# 赛道三赛题拆解 · 给 Multi-Agent 时代，造一个人还在场的工作台

> 最后更新：2026-09-04

## 一、赛题的两层含义（原文定义，路演必须回应）

「人还在场」被出题人明确定义为两件事：

1. **这一刻他管得住 Agent** —— 显性要求，容易演示。
2. **一年之后他自己也变强了** —— 出题人原话：「第二件事没有第一件显眼，**但它才是出这道题的原因**。」

⚠️ 设计含义：作品如果只做"管得住"（审批、观测、插话），只答了半道题。「决策流」机制③（翻案日志 = 这个人做了哪些判断的记录）恰好是对第二层的直接回应——人通过反复看见并翻案 agent 的决策，积累的是架构判断力，而记录本身就是成长证明。这一点在路演里应该点透。

## 二、硬边界（不满足即出局）

| 边界 | 原文依据 | 对方案的检验 |
|---|---|---|
| 把人拿掉，作品就不该还能正常工作 | 「一条全自动跑完、不需要人看一眼的 Agent 流水线……是开放创新组的地盘」 | 决策流没人看卡片就停在 ask 卡点上 → 天然满足 ✅ |
| 必须解决"人跟不上 Agent"的某一面 | 「工具是自由的，命题不是」 | 600 行 diff → 5 张决策卡，直接打"跟不上" ✅ |
| 能跑 + 解决自己真遇到的问题 | 「唯一的要求是它能跑」「最好的题目来源就是这两天半的你自己」 | 需要在赛期内用自己的工具吃自己的狗粮，留一手实录素材 |

## 三、四个参考方向与本方案的关系

方向是"参考不是限定"，但评审大概率按方向理解作品：

- **方向一（看得懂、管得住）**：决策流的主战场。注意出题方给的例子是"改动翻译器"（事后翻译 diff），research.md 已证实事后翻译被 review packet/CodeRabbit 做过——我们的差异是**改动发生之前**截住决策点，要在路演里主动划清。
- **方向二（多 Agent 不打架）**：不主攻。若时间富余，决策卡片流天然可扩展成"多 agent 各自的决策并到一个流里"，可作为 roadmap 一页带过。
- **方向三（不写代码的人指挥 Agent）**：顺手吃掉——卡片是中文判断题不是代码，非技术同学可以当"决策审核人"。FAQ 明确欢迎非技术同学，这是加分点。
- **方向四（Attribution）**：不做行级归因（已被 Cursor Blame/agentblame/git-ai 做死），attribution 降级为机制③的副产物："归因人的干预，不归因人的敲键"。同时避开与出题方知是"过程即作品集"的正面撞车。

### 2 分钟路演动线（research.md 已给出，赛题要求验证可行）

左边 agent 在跑 → 右边卡片冒出来 → 点一张、改一句 → agent 后续行为立刻变、之前的活没白干 → 弹出贡献报告。全程自解释，无需讲技术。
