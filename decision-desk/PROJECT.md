# 在场：让人的判断进入 Agent 的实际执行

Agent 可以很快完成网页，但它也会替人作决定：选布局、保留数据、增加登录。人经常直到看到成品才发现其中一项不符合原意。我们的项目把这些选择放到执行现场，并让人能够改变下一步。

在场是一个中文双栏工作台。左侧对照人的要求，右侧展示 Agent 准备做和已经做的事。普通选择继续执行；已识别的约束冲突在文件写入前暂停。人写一句纠正，旧动作被拒绝，新要求进入执行上下文，后续文件变化和对应检查记录下来。

## 两分钟演示

1. 选择“交互演示”，确认“免登录、不连接外部服务、刷新后清空报名信息”。
2. Agent 先生成卡片布局，蓝卡出现，任务继续。
3. Agent 准备将报名信息写入 localStorage，红卡出现，此时该写入尚未发生。
4. 输入“只使用页面内存，刷新后清空报名信息”，提交纠正。
5. 看到旧提案被拦停、后续修补完成、对应静态检查通过。切换“成果展示”，在宽屏或全屏页面中报名，再刷新确认清空。
6. 打开“判断与复盘”，查看人的决定、后续操作与检查证据，留下一句复盘并导出。

## 为什么这样取舍

我们保留 P 方案的独立审查和证据标准，采用 S 方案的双栏分层时间线，以 Y 方案的短约束、执行前拦停和向前纠正构成控制链。首版把一个人、一位执行 Agent 和一位独立审查器的闭环做好；多执行 Agent 与全局回滚留到后续。

界面不会把“没有操作”当作批准，也不会把“纠正已经注入”写成“Agent 已经遵从”。人的判断、执行动作和验证结果分别记录。这使复盘能回答：我改了什么，之后发生了什么，还有什么没有验证。

## 实际完成与边界

已实现真实 dsh 运行时、执行前门禁、停止与超时处理、异源模型接口、文件写入、内容哈希绑定的静态检查、中文工作台、隔离预览、复盘与导出。已通过 19 项单元/集成测试和 5 项浏览器测试。

演示模式使用明确标识的脚本执行器和规则审查，文件与控制链是真实运行的。真实模式接入两组兼容接口；当前只完成本地模拟服务的协议测试，尚未配置外部模型实测。我们不以演示成功推导真实模型的判定准确率，也不宣称这份记录已经证明人的长期能力提升。
